# Relationships

## Entity Relationship Summary

```
Student ──1:N──> WorkspaceSession
Faculty ──1:N──> WorkspaceSession (as recorder)
Admin ──1:N──> Category (as manager)
WorkspaceSession ──N:1──> Student
WorkspaceSession ──N:1──> Faculty (entry recorder)
WorkspaceSession ──N:1──> Faculty (exit recorder, may be same or different)
WorkspaceSession ──N:1──> Category
Student ──1:N──> Notification
WorkspaceSession ──1:N──> Notification
```

---

## Detailed Relationships

### Student → WorkspaceSession
- A Student **owns** many WorkspaceSessions
- A WorkspaceSession **belongs to** exactly one Student
- A Student can have at most **one** incomplete session (Created, Active, or Awaiting Summary) at any time
- A Student can have many completed and archived sessions

### Faculty → WorkspaceSession
- A Faculty member **records** many WorkspaceSessions
- A Faculty member may record the **entry** of a session
- A Faculty member may record the **normal exit** of a session (may be same or different faculty)
- A Faculty member may perform a **manual exit** as an exceptional action
- A WorkspaceSession has exactly one entry recorder
- A WorkspaceSession has exactly one exit recorder (normal or manual)

### Admin → WorkspaceSession
- An Admin may **override** a WorkspaceSession to complete or correct it
- An Admin may **archive** a Completed session
- Admin does not perform normal scanning

### Admin → Category
- An Admin **manages** Categories
- An Admin creates Categories
- An Admin archives Categories (soft removal)

### WorkspaceSession → Category
- A WorkspaceSession **must have** exactly one Category before reaching Completed status
- A Category **may be assigned to** many WorkspaceSessions
- A session may have no category during the Created state
- A session must have a category to become Active
- Category is mandatory for completion — "uncategorized" is not a valid concept

### WorkspaceSession → Notification
- A WorkspaceSession **generates** Notifications
- Entry generates an "entry" Notification
- Exit generates an "exit" Notification
- A session may generate reminder Notifications (category reminder, summary reminder)

### Student → Notification
- A Student **receives** many Notifications
- A Notification **belongs to** exactly one Student
- Notifications are generated by the System actor based on session events

### Student → Faculty
- Faculty interact with Students through the scanning process
- No persistent relationship exists; a Faculty member can record any Student's session
- There is no assignment or grouping of Students to specific Faculty

## Business Rationale for Relationships

### Why does a Session have one entry and one exit recorder?
The Faculty member scanning at entry may differ from the Faculty member scanning at exit (shift changes, different personnel). Both must be identifiable for accountability.

### Why does a Session belong to one Student?
A session represents an individual's attendance. Group sessions or shared attendance are not part of the domain.

### Why can a Student have only one active session?
A student can physically be in only one place at a time. Multiple simultaneous active sessions would indicate an error or abuse.

### Why are Notifications owned by the Student?
Notifications are about the Student's sessions and are delivered to the Student. Each notification concerns a single student.
